# Ares v1.1.0

Ares 1.1 productizes the operator-supervised security runtime and promotes governed reconnaissance into the supported product surface.

## Highlights

- Public Python distribution identity is now `bluedot-ares`.
- The `ares` import package and `ares`, `ares-dashboard`, and `ares-tui` commands remain unchanged.
- Governed autonomous reconnaissance uses a persistent attack-surface graph, explicit coverage ledger, and model selection limited to exact Ares-issued coverage IDs.
- Findings now preserve observation, hypothesis, corroboration, safe validation, reporting, supporting evidence, contradictory evidence, and limitations.
- Advanced operator validation requires same-mission evidence, exact task contracts, a digest-bound single-use approval receipt, applicable GhostMCP policy, and explicit high-risk approval.
- `ares doctor --json` and `ares support-bundle` provide supportable machine-readable diagnostics.
- Official release assets now include checksums, a CycloneDX SBOM, release metadata, GitHub build provenance, and SBOM attestations.
- Optional PyPI publication uses GitHub OIDC Trusted Publishing and does not require a long-lived PyPI token.

## Important package-name change

The PyPI project named `ares` is unrelated to this security runtime. Ares 1.1 is distributed as `bluedot-ares`.

New install:

```bash
pipx install bluedot-ares
```

Migration from the Ares 1.0.x GitHub wheel in an isolated pipx environment:

```bash
pipx uninstall ares
pipx install bluedot-ares
```

Ares state under `~/.ares` is not removed by uninstalling the Python distribution.

## Governed reconnaissance boundary

The autonomous planner can prioritize only passive and safe-active reconnaissance coverage. It receives no callable tools and cannot invent tools, targets, arguments, roles, task IDs, exploitation work, authentication attempts, persistence, or post-exploitation work.

Ares compiles the selected coverage ID into a fixed tool call and then applies the ordinary mission and dispatcher policy gates.

## Advanced validation boundary

The model does not select advanced tasks. An operator must provide the task graph and supporting evidence. Each advanced dispatch is bound to an expiring single-use approval receipt whose digest covers the exact mission, task, role, tool, target, arguments, and evidence.

## Fixed

- The nested `ares mission run` command now accepts and forwards `--approval-receipts`.
- The removed PySide6 GUI is no longer pulled through `requirements.txt`.
- Support and mission documentation now matches the autonomy and finding behavior on `main`.
- Package smoke tests no longer assume an `ares-*.whl` filename.

## Upgrade notes

1. Back up `~/.ares` before upgrading.
2. Remove the old `ares` distribution from the isolated environment.
3. Install `bluedot-ares`.
4. Run `ares doctor --json`.
5. Verify existing sessions and reports before starting new authorized work.

See [INSTALL.md](../../INSTALL.md), [the support boundary](../v1-support-boundary.md), and [release verification](../verifying-releases.md).
